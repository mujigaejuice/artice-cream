# 계정 삭제 구현·운영 확인

2026-10-08 구현. 현재 작업 트리 기준이며 아직 배포하지 않았다.

## 이용 경로

- 앱/웹: **나 → 계정 및 데이터 삭제**.
- 앱 밖: `/account/delete/`. 로그인 없이 서비스명·삭제 대상·절차를 읽을 수 있다. 로그인 화면에도 링크가 있다.
- 비로그인 또는 최근 인증이 없으면 가입 이메일로 확인 링크를 받는다. `shouldCreateUser: false`로 이메일 자동 가입을 막는다. Google 가입자도 해당 계정의 이메일을 사용할 수 있다.
- 요청한 브라우저·앱에서 링크를 열면 삭제 화면으로 돌아온다. 이메일 확인은 로그인만 수행한다. 표시된 계정을 확인하고 **계정 삭제**를 입력한 뒤 최종 버튼을 눌러야 삭제한다.
- API 성공 후 현재 기기의 세션을 정리한다. 기기 저장소 정리 실패와 서버 삭제 실패를 구별하여 안내한다.

## 서버 동작과 삭제 범위

[API](../../app/api/account/delete/route.api.ts)는 `GET`으로 계정과 최근 인증 상태를 확인하고 `POST`로 삭제한다. 응답은 `no-store`다. Bearer 토큰을 Auth 서버에서 검증하며 익명·미인증 사용자는 거절한다.

검증된 토큰의 인증 시각(`amr`)이 10분 이내인지 확인한다. 토큰 갱신 시각이나 다른 기기 로그인으로 바뀔 수 있는 사용자 마지막 로그인 시각으로 대신하지 않는다. 화면의 예상 사용자 ID와 서버 사용자가 다르면 거절한다. 삭제 대상은 항상 서버가 확인한 사용자 ID이며 임의 ID 지정 필드는 허용하지 않는다.

`auth.admin.deleteUser(user.id, false)`로 Auth 사용자를 영구 삭제하고 기존 외래 키가 다음 기록을 함께 삭제한다.

| 테이블 | 삭제 범위 |
|---|---|
| `profiles` | 해당 사용자 프로필 |
| `user_domain_levels` | 관심 분야·수준·최근 점수 |
| `user_article_progress` | 읽기·퀴즈 답안/점수·저장 기록 |
| `daily_quota` | 이용량 기록 |
| `ad_views` | 추가 열람 기록 |

개인 기록을 여러 요청으로 먼저 지우지 않고 Auth 삭제의 연쇄 동작을 사용한다. 외래 키가 삭제와 경합하는 뒤늦은 기록 재생성을 차단한다. 공유 기사·가공본·퀴즈와 Google 계정 자체는 삭제 대상이 아니다.

서비스 API는 Auth 사용자 존재를 확인하므로 삭제된 계정의 JWT를 거절한다. JWT 자체의 만료 시각을 앞당기는 구현은 아니다. 직접 DB 접근에서도 개인 기록이 조회되거나 다시 삽입되지 않는지 검증했다. 공유 콘텐츠의 RLS 정책은 이 작업에서 바꾸지 않았다.

## 검증

- `npm run test:account-delete`: 미인증·익명·다른 ID·확인 누락·오래된/누락된 인증 거절, 영구 삭제, 업체 오류 비공개, 동시 삭제의 `user_not_found`, 삭제 후 요청, CORS·복귀 경로. 실제 SDK와 HTTP 모의 사용.
- `npm run test:auth`: 웹 localStorage·네이티브 Preferences 정리와 삭제된 사용자의 403/404 응답 처리.
- `npm run test:logic`, `npm run typecheck`, `npm run build`, `npm run build:app`: 통과. Android 정적 번들에 공개 삭제 안내가 있고 서버 API는 포함되지 않는 점도 확인했다.
- 실제 Supabase: 전용 테스트 계정과 5개 테이블의 시험 기록 생성·삭제. 이메일 링크 인증, Auth/관련 기록 0건, 두 기기 JWT·갱신 토큰 차단, 직접·서버 지연 쓰기 재생성 차단, 공유 가공본 보존 확인. 기존 이용자나 기사 변경 및 이메일 발송 없음.

```sh
node --env-file=.env.local --import=tsx scripts/verify-account-deletion.ts
```

이 스크립트는 실제 DB에 시험 데이터를 만든다. 종료 시 자신이 생성한 이메일과 실행 태그가 모두 맞는 계정만 정리한다. 실패하면 정리 결과를 확인한 뒤 다시 실행한다. 실제 이용자 계정을 테스트에 사용하지 않는다.

연결된 브라우저가 없어 브라우저 UI 조작과 Android 실기기의 이메일 앱 왕복은 이번 검증에 포함되지 않았다.

## 배포 후 확인과 남은 과제

1. 기존 `0001_init.sql`의 연쇄 삭제 구조를 사용하므로 새 DB 마이그레이션은 없다. 다른 환경은 같은 FK 구성을 확인한다.
2. 웹/API 배포와 앱 번들 갱신 후 `/account/delete/`를 로그인 없이 열어 보고 실제 도메인의 URL을 Play 삭제 요청 URL로 등록한다.
3. Supabase의 기존 `/auth/callback`과 앱 딥링크를 그대로 사용한다. 로컬 복귀 힌트는 삭제 페이지 한 곳만 가리키며 1시간 후에는 무시한다. 인증 메일에는 기존 PKCE 링크가 필요하다.
4. 이메일·Google 가입 테스트 계정으로 링크를 요청한 브라우저/앱에서 열어 삭제 화면 복귀·계정 표시·최종 확인·취소·만료·실패를 확인한다. 다른 브라우저/기기에서 링크를 열면 PKCE 확인이 실패할 수 있어 다시 요청해야 한다.
5. 제공사 로그·백업 보관기간, 삭제 반영·복구 시 재삭제, 기간별 자동 파기와 별도 문의 창구는 아직 미확정이다. 공개 화면에도 서비스 운영 데이터와 이 범위를 구분한다. 개인정보처리방침이나 Play 제출 준비 전체가 끝난 것은 아니다.

참고: 서버 전용 [Supabase deleteUser](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser), [사용자 삭제와 JWT 주의사항](https://supabase.com/docs/guides/auth/managing-user-data). 이 프로젝트의 FK·세션 결과는 실제 통합 검사로 별도 확인했다.
